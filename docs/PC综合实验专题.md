# PC 综合实验：把采样、SOC、保护与通信接起来

> **本篇你会学到**　沿着一份日志追踪：电流怎样改变模型，采样怎样触发 C 状态机，状态怎样变成接收端的一帧。
> **预计用时**　首次跑通约 30 分钟，完成三道修改题约 1–2 小时。
> **前置**　读过阶段 3 的状态机、阶段 4 的 SOC 和阶段 5 的帧结构；已安装 Python 3.10+ 与 gcc。

这是纯 PC 的 4 串合成实验。模型、故障注入和阈值均为教学设置，不连接电池或 MOS。它验证软件信号链；1 秒一拍不能用来验证真实短路切断时间。

## 1. 一条命令跑通

在仓库根目录执行，Windows 的 `python` 也可换成 `py -3`：

```bash
python -m pip install -r code/requirements.txt
python code/firmware/pc_demo.py
```

入口会把原有 `bms.c` 与薄适配器 `pc_bridge.c` 编译到临时目录，执行完成后清理。支持 `--cc clang` 或通过 `--cc` 指定编译器路径。缺少编译器时会明确报错，不能把这一项当作通过。

输出目录是 `code/firmware/pc-demo-output/`。末尾应有 `"passed": true`，并列出 7 项检查为 `true`。默认输出 100 拍采样、99 帧有效遥测、1 次 CRC 错误。这些是可执行脚本的结果，不是电芯实测。

## 2. 每拍是谁先做什么

```text
负载/充电请求 → 上拍 MOS 输出决定本拍电流 → 四颗电芯模型
                                      ↓
                              量化采样 / 故障注入
                                      ↓
                    平均单体电压 → EKF → C 状态机
                                      ↓
                         本拍 MOS 输出与首次故障快照
                                      ↓
                  遥测组帧 → 坏字节注入 → 原有帧解析器
```

代码复用三个原有模块：[电芯模型](../code/soc/cell_model.py)、[SOC 估算器](../code/soc/estimators.py)、[C 状态机](../code/firmware/bms.c)与[帧解析器](../code/protocol/frames.py)。新增的 [pc_demo.py](../code/firmware/pc_demo.py)只负责编排；[pc_bridge.c](../code/firmware/pc_bridge.c)负责输入校验和输出，不重写保护逻辑。

**先采样，再决定下一拍。** 第 48 拍确认过充时，采样记录仍然有 2 A 充电电流；切断输出影响第 49 拍。这是离散仿真的时间顺序，不能把切断后的零电流倒填进触发故障的现场。

四颗模型的初始 SOC 略有差别，均衡输出会在下一拍对相应模型施加 0.15 A 的示例泄放电流。这里的 `soc_mean_true` 与 `soc_mean_est` 表示**四颗电芯的平均 SOC 及其估计**，没有实现整包最弱单体约束下的可用容量估算。

## 3. 按时间找到故障

日志中的 `tick` 从 1 开始；代码里的场景索引 `k` 从 0 开始。

| 拍次 | 输入场景 | 要观察的结果 |
|---|---|---|
| 1–5 | 静置 | 初始化后进入待机 |
| 6–25 | 请求充电 | 状态进入充电或均衡 |
| 26–45 | 请求放电 | 均衡退出，按放电方向运行 |
| 46–50 | 第 0 串采样固定成 4300 mV | 第 48 拍去抖满，禁充、保留放电恢复路径 |
| 51–60 | 撤掉故障采样，请求放电 | 恢复条件满足后退出故障态 |
| 61–65 | 电流采样固定成 −31000 mA | 第 61 拍报告短路并双断；首次快照仍是过充 |
| 66–70 | 卸载 | 电流回到解锁窗口 |
| 71–75 | 温度采样固定成 650，即 65°C | 报告过温并双断 |
| 76–90 | 恢复温度，再放电与充电 | 检查恢复和后续正常迁移 |
| 91–100 | 静置 | 观察待机与休眠计数 |

过充、短路和过温由**采样端注入**：模型本体没有被加热，也没有模拟外部短路的电磁暂态。`actual_a` 是模型电流，`current_ma` 是送给估算器和状态机的采样；短路注入期间两者刻意不同。这个差异也会干扰 SOC，日志保留干扰结果。

## 4. 五份产物怎样读

| 文件 | 用途 |
|---|---|
| `samples.csv` | 每拍请求电流、模型电流、量化采样、SOC、状态、MOS 和快照字段 |
| `telemetry.csv` | 接收端真正解析出的物理量；第 13 拍应缺失 |
| `wire.bin` | 实际送入解析器的完整字节流，含一个坏 CRC 帧和垃圾前缀 |
| `events.json` | 状态或故障掩码改变时的现场记录 |
| `report.json` | 去抖、切断反馈、快照保持、过温及通信一致性的验收结果 |

`events.json` 是 PC 端日志；`snapshot_*` 才是固件骨架保存的首次故障。骨架没有新增 NVM 存储，也没有改变“上电以来第一次故障”的快照生命周期。

在 `samples.csv` 对照第 48、49、61 拍，再到 `telemetry.csv` 找相同拍次。第 61 拍的当前故障应该是 `SCD`，快照原因仍应是 `OVP`，快照拍次仍是 48。

## 5. 遥测协议表

外层复用教学帧 `AA 55 | addr | cmd | len | payload | crc8`。本实验地址为 1、命令为 `0x10`、载荷长 24 字节。整数使用大端，CRC 覆盖地址到载荷；不是商用 BMS 协议。

| 载荷偏移 | 字段 | 编码与单位 |
|---|---|---|
| 0–3 | tick | uint32，拍次 |
| 4 | state | uint8，依次为 INIT、STANDBY、CHARGE、DISCHARGE、BALANCE、FAULT、SLEEP |
| 5 | SOC | uint8，百分数 |
| 6–7 | fault_mask | uint16，bit0–4 为 OVP、UVP、OCD、SCD、OT |
| 8 | MOS | uint8，bit0 充电、bit1 放电，1 表示导通 |
| 9 | balance_mask | uint8，bit0–3 对应四串 |
| 10–13 | 电流 | int32，mA，充正放负 |
| 14–15 | 温度 | int16，0.1°C |
| 16–23 | 四串电压 | 四个 uint16，mV |

第 13 帧被故意破坏 CRC；第 33 帧前加入三个垃圾字节。接收器逐字节消费，**只在整个流结束时调用 `flush()`**。任意读取分块都不被冒充为帧间超时。

## 6. 三道修改题

1. **改去抖。** 在 `pc_bridge.c` 把过充去抖从 3 改为 4，先写下预计触发拍次，再运行。原验收应报失败；找到变化后的拍次并说明为什么，最后恢复示例配置。
2. **改坏帧位置。** 在 `pc_demo.py` 把 CRC 损坏移到另一个索引。预测接收日志缺哪一拍，再核对 `wire.bin`、接收行数和下一帧是否找回。
3. **解释估算污染。** 对照短路注入前后的 `actual_a`、`current_ma` 与 `soc_mean_est`，说明为什么一份错误电流采样会同时触发保护并干扰积分。

提交你的预测、实际日志和差异解释。不要只交 `passed: true`；修改实验后，应先理解哪项原验收不再适用，再决定是否调整它。
