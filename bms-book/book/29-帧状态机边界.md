# 第 29 章 帧状态机的八个边界

::: story 现场
100 帧遥测，第 13 帧被异或坏 1 个字节，第 33 帧前面还插了 3 个垃圾字节 `00 ff 19`。解析器丢掉坏帧、计数 `bad_crc: 1`，把后面的 87 帧全部收回，最终 `received_frames: 99`、`resyncs: 4`。这 4 次里**只有 1 次**来自坏帧，另外 3 次由 3 个垃圾字节各触发一次。

这不是“运气好”。这是设计：**坏帧只排除当前帧头，余下字节重新扫描；孤立帧头留到下一字节。**
:::

## 29.1 字节布局

```
AA 55 | addr | cmd | len | data[len] | crc8
```

- `addr`：从机地址；
- `cmd`：命令；
- `len`：数据长度，单字节；
- `crc8`：CRC-8/ATM，覆盖 `addr..data`。

CRC-8/ATM 的实现只有几行：

```python
crc = 0
for byte in data:
    crc ^= byte
    for _ in range(8):
        crc = ((crc << 1) ^ 0x07) & 0xFF if crc & 0x80 else (crc << 1) & 0xFF
```

## 29.2 八个边界

1. **帧头跨分块**：末尾孤立的 `AA` 要留到下一字节；
2. **载荷里有 `AA 55`**：合法帧内的不抢帧头；
3. **长度非法**：`len > MAX_LEN` 只排除当前帧头，重新扫描；
4. **CRC 错**：丢弃并计数，不能静默；
5. **残帧**：只有明确超时/流结束才 `flush()`，不能把每次 `read()` 当超时；
6. **长度 0**：总长是 `6 + len`，仍有帧头、元信息与 CRC；
7. **负下标**：字段解码要显式拒绝负数，Python 的负索引会从尾部回绕；
8. **内嵌好帧**：载荷里即使有一个完整合法帧，也按载荷保留。

::: principle 一句话
坏帧要分类计数；重同步只丢弃已经证伪的字节；残帧保留到明确的超时或 `flush()` 边界。验收时分别检查这三个动作。
:::

## 29.3 自己跑一遍

`code/frame_parser.py` 构造了一段带垃圾前缀、坏 CRC、残帧的字节流：

```text
有效帧 1 + 垃圾 00 11 22 + 坏 CRC 帧 + 有效帧 2 + 半截帧
```

输出：

```text
frames: [('0x1', '0x3', '0ea00eb4'), ('0x2', '0x5', '0102')]
ok/bad_crc/bad_len/incomplete/resyncs: 2 1 0 1 5
```

两帧好帧都回来了，坏 CRC 计数 1，残帧计数 1，重同步 5 次。那 5 次拆开看：垃圾 `00 11 22` 占 **3** 次、坏 CRC 帧重扫占 1 次、`flush()` 后清尾占 1 次。**一次重同步 = 一次「丢掉已证伪的字节」，不是一次「出故障」**：字节是一个一个喂进去的，3 个垃圾字节就是 3 次独立的丢弃。所以 `resyncs` 大不等于链路坏，它只说明解析器丢过多少次无主字节。逐字节喂入与整段解析结果一致。

## 29.4 真实协议

教学帧是抽象。真实项目里：

- JK-BMS 的 UART/BLE 帧有固定头、长度、命令、CRC；
- 不同型号/固件的寄存器与缩放可能不同；
- 厂商文档常常缺失，需要抓包 + 已知量对照。

BMS-Z 阶段 5 按使用场景区分这些接口：UART 常见于私有调试协议，CAN 常见于车辆网络，Modbus 常见于储能设备。

解析器只证明字节结构成立，不证明语义可信。真实协议还要继续核对缩放、端序、固件版本、滚动计数器和信号新鲜度：一帧 CRC 正确的“3 秒前 SOC”，结构上完全合法，控制上仍然过期。第 18 章负责端到端数据身份，本章负责把原始字节安全地交上去。

## 29.5 有界缓冲与单调进展

解析器要能在噪声里跑一整夜，先写三条不变量：

1. **候选长度有上界**：`MAX_LEN=64`，完整帧总长为 `2 + 3 + len + 1`，所以最大候选帧是 **70 B**。无帧头的垃圾立即丢弃，只在末尾保留一个可能跨分块的 `aa`；不能让噪声把缓冲拖成无限日志。
2. **循环每轮必须进展**：要么吐出一帧，要么至少丢 1 个已证伪字节，要么因为缺字节返回等待。不存在“条件不变却继续 while”的第四条路，否则坏流量能把 CPU 锁死。
3. **只删除已经证伪的最小前缀**：坏长度或坏 CRC 时只删当前候选帧头的第一个 `aa`，余下字节重新找头。整段候选一起扔，会把坏外层载荷里两条完好的内嵌帧一并吞掉。

发送端也要守同一条 64 B 上限：允许组出 65 B 载荷、再让自己的接收端拒收，是往返契约自相矛盾。字段层同样要显式拒绝负索引；Python 的 `-1` 会静默读成最后一串，不是“越界报错”。

## 29.6 验收矩阵：计数器必须能解释现场

**表 29-1**　帧解析器注入用例与预期计数（`frame_parser.py` 回放值）

| 注入 | 预期输出与计数 | 绝不能发生 |
|---|---|---|
| `00 ff 13 37` + 好帧 | 好帧照收；`resyncs` 增加 | 垃圾前缀让解析器卡死 |
| 帧头跨两次 read | 第一次保留 `aa`；第二次继续 | 每次 read 后 flush |
| `len=255` 后跟好帧 | `bad_len +1`；后帧恢复 | 按 255 B 一直等，或连后帧一起丢 |
| CRC 错帧载着两条好帧 | `bad_crc +1`；两条内嵌好帧恢复 | 整个坏候选一次清空 |
| 合法载荷内含 `aa 55` | 只输出外层帧 | 载荷抢占当前帧头 |
| 合法长度残帧 + 明确超时 | `incomplete +1`；重新扫描余字节 | 普通分块结束就记残帧 |
| 0 B / 64 B 载荷 | 都能往返；总长分别 6 B / 70 B | 边界差一位或发送端放宽上限 |

`bad_crc`、`bad_len`、`incomplete`、`resyncs` 不是四个“越多越坏”的 KPI，它们各自回答一个问题：`bad_crc` 问完整性，`bad_len` 问长度契约，`incomplete` 问时间边界，`resyncs` 问重新对齐。验收报告要给原始字节片段、首次异常时间、各计数增量与恢复后的第一条好帧；只给总错误数，无法定位是哪一层坏了。

::: trap 坑
把串口 `read()` 的分块当帧边界。一次 `read` 可能给你半帧，也可能给你三帧；只有超时或显式长度才能定界。
:::

**结构合法不等于可信：CRC 过了，这串字节就能进控制决策吗？**

帧头、长度和 CRC 通过，只能说这串字节符合某种结构，未发现校验矛盾。它没有回答发送者是谁、这一帧多旧、字段比例是否用对。旧数据原封不动地再发一次，也能通过 CRC。结构检查之后还要核对身份、版本、滚动计数器与时间戳，才能决定这份数据现在能否进入控制。

**教学算例：沿着这组输入做一遍**

1. 先约定串口示例是每字符 10 位；字节时间=10÷波特率。
2. 9600 bit/s 对应约 1.042 ms，115200 bit/s 对应约 0.087 ms；这只算线上传输时间。
3. 即使传得很快，缓冲区中的读数仍可能已经过期。另查采样时间与年龄，不能用短字节时间证明新鲜。

**边界与反例**　10 位是这里的串口格式示例；带校验或不同停止位时要按实际位数算。CRC 不是身份认证，更不能从校验余数唯一定位坏位。

**单变量定位字段：没有协议文档，怎么把一串字节认成电压？**

未知报文里哪两字节代表电压，不能靠数值看着像来猜。先固定其他条件，只改变一个已知量，再把多帧竖着对齐，找随它变化的列。找到候选后，用两个已知点解比例与偏移，再用第三种工况反证。一次同时改变电流、温度和电压，会让关联关系缠在一起，无法辨明原因。

**教学算例：沿着这组输入做一遍**

1. raw=3700 对应 3.700 V，raw=4150 对应 4.150 V，比例为 (4.150−3.700)/(4150−3700)=0.001 V/LSB。
2. 把任一点代回 V=a×raw+b，得到示例偏移 b=0。
3. 若 raw 实际是 370 对 3.700 V，比例就可能是 0.01；再查端序、带符号与版本，不能凭一帧定字段。

**边界与反例**　两个点只确定线性候选，不证明在全范围都成立。CRC 程序先拿已知协议帧验证，避免把程序错误和协议猜错混在一起。
