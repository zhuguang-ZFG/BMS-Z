# 维护说明

本文面向维护者：CI 在守什么、本地门在守什么、发布与回填的顺序、哪些坑别再踩。读者请直接看文档站。

## 这仓库里有什么

- 五个阶段 × 每阶段 5 篇，25 篇教程 + 25 张电路图（阶段 1 的 5 张是静态接线图，阶段 2–5 的 20 张是 SMIL 动画）+ 阶段 3 起每篇一篇进阶短文（阶段 3/4 各 5 篇、阶段 5 共 6 篇）+ 一个总索引 + 一份工具清单。张数由 `check_animation_claims()` 从 `docs/circuits/assets/*.svg` 现数，再和 25 处手写字面量逐个对账，人只改字面量，永远不手改张数。
- 每篇教程结构固定：前言 → 硬件清单（表）→ 接线（图）→ 逐步实现（编号步骤）→ 代码（完整 `.ino`，可按文件直接编译）→ 验证步骤 → 常见问题（表格）→ 下一步。相关概念一律链到 [BMS 名词与基础知识](terms.md) 与 [常见问题](faq.md)，不在正文里重写第二份。
- 电路图与教程正文在同名目录（`docs/circuits/`），正文相对引用图片，图内中文用 Noto Sans SC；仓库不存 PDF 版电路图，PDF 只有构建产物。
- 皮肤是 VitePress 默认主题加一份自定义 CSS（[custom.css](.vitepress/theme/custom.css)），没有第三方主题。中文排印增强（标点悬挂、标点挤压与中西文间距）只挂在 `.vp-doc` 阅读容器上，代码块显式还原；离线书籍由 `bms-book/build_html.py` 内联同一套栈。
- [首页](../index.md) 与 [学习路径](learning-path.md) 是给读者的两篇门面；[更新动态](news.md) 按发布批次分组；[资料页](resources.md) 的推荐阅读与页面内容不重复。各阶段首页的「教程一览」表与本阶段页由 `check_stage_toc()` 互相对账。

## 共建入口

- 新手任务（错别字、链接、FAQ 补充）在 [CONTRIBUTING](../CONTRIBUTING.md)；每周任务板在 [共建任务板](共建任务板.md)，含认领流程与完成定义；长期路线与决策记录在 [ROADMAP](ROADMAP.md)。
- 讨论区 [Discussions](https://github.com/zhuguang-ZFG/BMS-Z/discussions) 有 11 个分类，其中 7 个已配置发帖模板（打卡、求助问答、作品展示、保护板、算法、协议、固件），模板文件名必须等于分类 slug，改名要对回 `.github/DISCUSSION_TEMPLATE/`。

## 动画维护（阶段 2–5）

电路图是带 SMIL 动画的 SVG，维护要点：

- 底图：Inkscape 画静态层 → 标出电流路径 → 导出「优化后的 SVG」。
- 动画：手写 `<animate>` 标签，`attributeName="opacity"` 控制元件高亮，`stroke-dasharray` + `stroke-dashoffset` 控制电流流动。时长 6–12s，`repeatCount="indefinite"`。
- 命名：`阶段X-名称.svg`，在 `docs/circuits/index.md` 索引表中登记路径、说明、动画时长。
- 正文引用：`![阶段X 名称](circuits/assets/阶段X-名称.svg)`，不需要 `<!-- -->` 锚点，标题自动成为锚点。

## 站点图片

- 图片放 `docs/.vitepress/public/images/`，正文用根路径引用，例如 `![alt](/images/xxx.svg)`。
- 已知：VitePress 内置的图床优化（`createContentLoader` + `content.properties`）不兼容 Windows 路径分隔符。相关功能（图片懒加载等）关闭，用标准 Markdown 图片语法即可，构建正常。
- VitePress 的默认图片缩放插件依赖 `element-plus`，不兼容当前主题，不使用。

## 新增一篇教程的步骤

1. 文件放 `docs/stage-X/`（阶段 1–5），命名 `NN-名称.md`，NN 是该阶段内序号。
2. 在 `docs/.vitepress/config.mts` 的 `sidebar` 数组对应阶段里加入口，否则侧边栏不显示。每篇教程首页的锚点链接（如 `[第一阶段](#第一阶段-保护板基础)`）会自动生成，不需要手动加 `<!-- -->`。
3. 如果附电路图/动画，图片放 `docs/circuits/assets/`。
4. 首页与阶段的「教程一览」表如声称「每阶段 5 篇」，需手工同步更新对应行。
5. 构建验证：`pnpm docs:build`（或 `npm run docs:build`）。
6. 三个模板（教程、阶段首页、README 表格行）在 CONTRIBUTING。

## 分支与合并

- 主分支 `main`，直接 push 或 PR 合并都可以，但合并前 CI 必须绿。
- CI（`.github/workflows/`）
  - `tests.yml`：ruff → check_docs.py（文档结构完整性 + 21 类事实声明）→ docs 构建 → check_pages.py（页面数/链接数/锚点）→ check_search.mjs（Pagefind 索引完整性）→ 固件冒烟（gcc 编译 + 单元冒烟）。
  - `links.yml`：lychee 全站链接巡检（`.lychee.toml` 排除 16 个反爬域名）。
  - `deploy-pages.yml`：main 分支构建 + 部署到 GitHub Pages。
- 本地跑 CI 同款检查：`bash scripts/local-gates.sh`（Linux/Mac）或 `scripts/local-gates.ps1`（Windows）。脚本会依次跑 ruff、pytest、check_docs、构建、check_pages、check_search、固件冒烟。
- **注意**：路径结尾的点或空格在 Windows 上会被静默吞掉，导致本机检查误报通过。遇到本机绿但 CI 红，先怀疑这类路径问题。

## 发布流程（v1.4.0 起启用）

版本号格式 `vX.Y.Z`，标签打在 main 上。

1. **起草**：CHANGELOG 的 `## [Unreleased]` 累积条目，够了就建 `## [1.4.0]` 小节，把 Unreleased 条目**搬**（不是复制）进去，写节首那句（`python3 tools/release_stats.py` 生成）。
2. **定稿**：RELEASE_NOTES.md 只保留当前版，过期内容归档到 CHANGELOG。
3. **打标签**：`git tag -a v1.4.0 -m "v1.4.0"` → `git push origin v1.4.0`。CHANGELOG 里 `## [1.4.0]` 的小节名**不带 v**（`changelog_sections()` 不认 `## [v1.4.0]`），但 `releases/tag/v1.4.0` 链接里的标签**带 v**。
4. **建 Release**：GitHub 上基于该标签创建 Release，正文贴 RELEASE_NOTES.md，发布后立即核对 Release 页面的发布时间。
5. **回填（一次收口提交）**：CHANGELOG 加发布记录表行、更新动态加分组、README/README 维护节/门户三处版本号。
6. **验证**：三处门面（README 徽章、README 折叠块、门户卡片）、发布记录表、更新动态、`--release-truth` 全绿再合。

回滚：删掉标签与 Release，改回文件。

## 两道门

CHANGELOG 的发布记录表是「发布凭据」，由两道门对账：

- 文本侧（CI 的 check_docs.py）：表头 13 列、每行 14 格（多出来的最后一格是 compare 落款）、版本号递减、外链 slug、表行必须晚于 GitHub Release（"先归档、再打标签"的顺序做不到绿，v1.4.0 起顺序改为 标签 → 推标签 → 建 Release → 一次收口提交做完「归档 + 表行 + compare 落款 + 三处门面 + 更新动态分组」）。
- 真值侧（`python3 tools/release_check.py --release-truth`，本地跑）：用 `gh` 现取标签 sha → 提交 sha、`publishedAt`、Release 正文、三个 workflow run 号，逐项和表里对。不进 CI（runner 上的 `gh` 没凭证、fetch-depth 1 数不到标签）。

细节见 [CHANGELOG](../CHANGELOG.md) 的 1.3.0 小节与本页「21 类事实声明」。

## 21 类事实声明（CI 文本侧，check_docs.py）

**理念**：声明与真值分家，错数会静默上线；`check_docs.py` 把正文里的数字、日期、列表、表头、slug、存在性声明分 21 类对回仓库现值。新增事实声明时，在 check_docs.py 里加一类。

各阶段页首的数字（电压/电流/串数）来自各阶段首页，`check_stage_frontmatter()` 现算现对；Changelog 与更新动态的版本号、README 与门户的「最近更新」`v1.3.0` 胶囊、GitHub 仓库描述、Discussions 分类数、`.lychee.toml` 排除域名清单，全部对账。

**对不上的写法只有两种下场**：门报红，或者门读不到（`docs/.lychee.toml` 域名清单改写法 → 旧正则读不到 → 门当「没写」放行 → 域名烂掉 CI 不报）。这 21 类的正则只能收紧不能放宽，放宽前先在 issue 里论证。

## 本地门

`check_docs.py` 里 `LOCAL_STEPS` 标注的门只在本地跑（runner 上缺 git 历史 / gh 凭证）：发布记录对账、分类真值、仓库简介对账。本地门全绿再推。

## 提交与合并节奏

- 小步提交，一个逻辑改动一个 commit。
- CI 红了先看是不是 `.lychee.toml` 里那 16 个反爬域名（月检一次，手动浏览器确认还活着）。
- 文档类的 PR 合并前至少本地跑一遍 `bash scripts/local-gates.sh`。

## 已知坑（别再踩）

1. Windows 路径结尾 `.` / 空格被吞。
2. VitePress 图片优化与 Windows 路径分隔符不兼容。
3. lychee 在 CI runner 上访问某些域名会 403/超时（反爬），换成本机网络再确认。
4. 阶段首页「教程一览」表是手写的，新增教程后忘改表 → CI 红。
5. 仓库刚建时把 `docs/` 嵌套进了另一个 git 仓库，导致 push  rejected。如果 clone 下来看不到 docs/ 下的文件，检查是不是嵌套仓库问题。
6. `actions/checkout` 默认 `fetch-depth: 1`，数不到标签。要用 `git describe --tags` 必须加 `fetch-depth: 0`。
7. lychee 对同一个 URL 在 push 和 PR 事件下表现不同（HEAD vs merge commit）。
8. Release 记录表行必须晚于 GitHub Release 发布时间，"先归档、再打标签"做不到绿。
9. `lychee` 的 `--exclude` 正则不锚定，会误伤同字符串的其他 URL。
10. CHANGELOG 小节名 `## [1.4.0]` 不能写成 `## [v1.4.0]`（对账脚本只认前者），但 `releases/tag/v1.4.0` 链接要带 v。
11. `textlint` 未启用。启用后跑 `textlint --fix` 会把全角标点批量替换成半角，破坏现有格式，不要启用。
12. 构建 VitePress 时 `docs/.vitepress/cache` 和 `dist` 要加到 `.gitignore`，否则 push  rejected（大文件）。
13. GitHub Pages 部署后缓存 5–10 分钟，刚部署完看不到更新是缓存，不是没部署成功。
14. 推 tag 后 GitHub 自动生成的 Release 是 draft，要手动 publish；自动生成的 tar/zip 不含子模块，源代码包要自己传。
15. Release 的 `published_at` 比推 tag 晚几分钟，脚本对时留 5 分钟缓冲。
16. `vp-update` 升级 VitePress 后默认主题 CSS 变量名可能变，自定义皮肤要跟着改。
17. SMIL 动画在部分 Android WebView 上不自动播放，给每张图配静态 fallback PNG 并在正文同时引用。
18. `git log --format=%s` 取 PR 号会漏 squash 之外的合并方式，PR 号用 `gh pr list --state merged` 更稳。
19. 每次发版要手动改三处门面（README 徽章、README 折叠块、门户卡片），`check_latest_claims()` 会守，但门面多了容易漏。
20. 目录名带空格或中文，lychee 输出会截断，排查死链时先 `lychee --verbose` 看完整 URL。
21. Windows 下 `pnpm docs:build` 的符号链接需要管理员权限或开发者模式，否则用 `npm run docs:build`。
22. GitHub Actions 的 `GITHUB_TOKEN` 默认只读 `contents`，workflow 里要用 `gh` 必须显式给 `permissions:` 写 `contents: write` 和 `pull-requests: write`。
23. SMIL 的 `stroke-dashoffset` 动画在 Safari 上可能卡顿，改用 `opacity` 闪烁更稳。
24. VitePress 侧边栏数组不存在的路径会构建警告但不报错，新增教程后忘加 sidebar 不会红，只会静默不显示。
25. `gh release view` 的输出格式在不同版本 `gh` 之间有差异，脚本里用 `--json` 显式指定字段。
26. 仓库描述（About）里的动画张数在仓库设置里，任何文件都对不上它，要单独对账。
27. 社交预览图 `bms-roadmap-social.png` 是手工位图，教程数/动画数变了不会红，要单独对账。
28. 本地门脚本的头注释、CONTRIBUTING、本文的步骤清单是三份抄本，加门时三处一起改。
29. `fetch-depth: 0` 在私有仓库会拉全部历史，大仓库 CI 明显变慢，只在需要 tags 的 job 上加。
30. 两张 .gitignore（根目录 + `docs/`）要同步维护，新增构建产物目录时两处都加。
31. Stage 3/4/5 进阶短文的「回到教程」链接和父教程的「进阶阅读」链接要互相指着，漏一边读者就断。
32. `actions/labeler` 的 `sync-labels: true` 会把手动加的 label 清掉，不用 sync。
33. PR 合并后 tag 还在原分支上，`git describe` 显示的是旧 tag，要 `git fetch --tags` 再 describe。
34. `check_release_record()` 只比小节集合，同一条目在 Unreleased 和版本节各留一份时两边照样自洽——收口是「搬」不是「复制」，这道门不管，靠 `check_release_archive()`。
35. 更新动态的分组行不在 `check_latest_claims()` 的锚点里，靠 `check_release_dynamic()`。
36. check_docs 的门对「正则认不出的写法」静默放行——正则只能收紧，放宽要在 issue 论证。
37. 本地门缺 `gh` 时记 SKIP 不算 FAIL，但「都等于 git 与 gh 的现值」那句 ok 不能打——跳过路径只打注意行。
38. `.ps1` 本地门脚本必须存成 UTF-8 with BOM（PowerShell 5.1 要求），但门脚本自己读它要用 `utf-8-sig`，否则行首 U+FEFF 让注释块判空。
39. check_docs 的第一步「strip fenced/inline code 再提链接」，正文里的 Markdown 写法示例（反引号包裹的 `![...](...)`）不是链接；不剥会被报成死链。
40. runner 上 `check_release_counts()` 数不到标签是设计（`check_runner_no_tags()` 守这句根据），真值门不进 CI。
41. 动画张数门面有 25 处写法，新增第 26 处时 `check_animation_claims()` 的句数反查会红——把新写法加进 `ANIMATION_CLAIM_RES`。
42. `check_release_dynamic()` 扩到每一个分组后，历史分组可以整组缺席或 omit 日期，但版本号必须在表里、写了日期就要对、组下不许空、不许重复。
43. `tools/release_stats.py` 与 `check_release_counts()` 是两套实现，措辞由 `check_release_wording()` 的 round-trip 门钉住，改措辞要两边一起改。
44. `check_local_gate_lists()` 以脚本实际吐出的 PASS 标签为真值，箭头串名字要逐字照抄脚本，散文别名不算。
45. 「前八步／后五步／这五样」里的数 = 总步数 − 本地道数，且必须写在箭头串同一行。
46. 发布记录表里「收口提交」和「核验」那两列允许先写「未记录」再回填，其余列不行。
47. 标签 → Release → 收口提交这段窗口里 `--release-truth` 必红（"git 有标签 v1.4.0，发布记录表没有这一行"），是顺序的正常产物，别提前填表。
48. 节首那句「共 N 条」与「覆盖 M 个提交」从 v1.4.0 起不是同一个窗口：前者数到 HEAD，后者数到标签。别为了让它们对齐把 M 改成数到 HEAD。
49. `check_changelog_counts()` 只读 `## [X.Y.Z]` 小节，Unreleased 是下一版账本，加条条目不判。
50. `check_changelog_enum()` 用 `CL_HEADING` 与 `changelog_sections()` 的小节集合互验，一节都认不出直接判「后面几道门全是空跑」。

## 链接巡检

全站链接由 lychee 巡检（`.github/workflows/links.yml`），排除清单在 `.lychee.toml`。被排除的 16 个域名每月手动点一次。`archive.org` 已移出排除（2026-10-07 复查 details/metadata 均 200）。

## 皮肤（自定义 CSS）

皮肤只有一处自定义：[custom.css](.vitepress/theme/custom.css)。改动原则：

- 可读性优先：行宽、字号、行高、段距、对比度。
- 动效只做一次（`:hover`、页面加载），不做循环动画。
- 装饰只做边线、留白、圆角与一层浅影。

中文排印增强（2026-10 新增）：

- 标点悬挂与挤压走 CSS Text 4：`text-spacing-trim: trim-start` 挂在 `.vp-doc`，整段只认四值写法（Chromium 151 起支持；两值/三值简写落在旧解析器上整条不生效），代码块 `<pre>` 显式还原为 `normal`，中西文自动间距用 `text-autospace: normal`（Baseline 2025-11 起，属视觉层属性，行高盒不变）。字体栈补了 MiSans / OPPO Sans / HarmonyOS Sans SC，iOS 落 PingFang SC。
- 全站打印兜底：新增 `@media print` 块（@page 边距 14mm/13mm/16mm、隐藏导航与面包屑），`.book-reading` 阅读模式覆盖阴影与表头底色；速查卡另有专属打印块，特异性更高，两处不冲突。
- 以上只挂阅读容器，不进代码块与表格数字。

速查卡打印版在速查卡页自带 `@media print`（在 `custom.css` 末尾）。离线 HTML 书籍（`bms-book/`）由 build_html.py 生成，构建时内联同样式。

## 命名约定

- 文件名：kebab-case，目录小写。阶段目录 `stage-1/`…`stage-5/`。
- 图片：`images/` 放共享图，`circuits/assets/` 放电路图。

## 维护者交接清单

新维护者接手时按顺序：

1. 读 README、CHANGELOG、ROADMAP。
2. 跑一遍 `bash scripts/local-gates.sh` 看是否全绿。
3. 翻一遍本文「已知坑」。
4. 挑一个 [共建任务板](共建任务板.md) 上的新手任务走一遍 PR 流程。
5. 发一次 patch 版本（改错别字 → v1.X.Y+1）。
6. 发一次 minor 版本（加一篇进阶 → v1.X+1.0），走完整发布流程。
7. 做一次月度链接巡检（手动点 `.lychee.toml` 排除的域名）。
8. 复盘一次 CI 红（把当月所有红 run 归因分类，看哪类门最容易误报）。
9. 检查 Discussions 有没有过期待回的帖子。
10. 把本次维护心得补进本文。

## 排查清单

遇到 CI 红，按顺序查：

1. 是不是 `.lychee.toml` 里 16 个反爬域名的锅？
2. 是不是 fetch-depth / gh 权限问题？
3. 是不是 Windows 路径空格/点问题（本机绿但 CI 红）？
4. 是不是 VitePress 缓存（`docs/.vitepress/cache`）没清？
5. 是不是新增教程忘加 sidebar？
6. 是不是动画张数字面量没同步（25 处 + 简介 + 社交卡）？
7. 是不是发布顺序问题（标签 → Release → 收口提交）？
8. 是不是正则写法漂移（对账门静默放行）？跑一遍 `check_docs.py --verbose` 看哪类门没捞到。
