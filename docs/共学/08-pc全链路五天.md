# 共学：PC 全链路五天

> **本篇你会学到**　采样、估算、保护、通信这四块在**一拍之内**到底谁先谁后：一台真 C 状态机收到 4 串电压和电流后，怎么在三个采样里去抖出过压、怎么用一次切断影响下一拍、怎么在整条流里扔一个坏 CRC 帧还能把剩下 99 帧收全。
> **预计用时**　5 天，每天大约 30–60 分钟。
> **前置**　做过 [固件五天](03-固件五天.md) 或读过 [阶段 3 §3.4](../stages/stage-3-AFE-MCU智能BMS.md)。装好 Python 3.10+、在仓库根 `pip install -r code/requirements.txt`，并且 PATH 里有 `gcc`。不接电池。

⚠️ 本篇是**PC 综合仿真**：电芯是 [Thevenin 模型](../stages/stage-4-SOC-SOH算法.md)，故障是**采样端注入**（脚本把某一拍的电压或电流改成故障值），C 状态机是仓库里那份原版 `bms.c`。内部管道不是串口，1 秒一拍**不是**硬件保护时序——真实短路保护是微秒级（见 [短路保护：微秒级的反射神经](../circuits/assets/short-circuit-timeline.svg)）。深读版在 [PC 综合实验专题](../PC综合实验专题.md)，本篇是五天节奏＋打卡。

## 第 2 天：三个采样才动一次手

**读**　[保护去抖与回差](../circuits/assets/protection-debounce.svg) 的图说与 [阶段 2 §2.2](../stages/stage-2-保护板实践.md)：电压越过阈值**不立即断**，要连续确认若干采样；恢复也不是回到同一根线，而要落回更低的回差线。

**看**　[保护去抖与回差动画](../circuits/assets/protection-debounce.svg)。去抖 20 ms 计满才动作，恢复要落回 4.15 V 的回差线以下——今天在真实采样序列上把这条讲一遍。

**跑**（把过压注入那几拍取出来看）：

```bash
python3 -c "
import csv
rows=list(csv.DictReader(open('code/firmware/pc-demo-output/samples.csv',encoding='utf-8')))
for r in rows[44:50]: print(f\"tick={r['tick']:>3} cell0={r['cell0_mv']:>4} fault={r['fault']:<5} chg={r['charge_on']}\")
"
```

2026-10-09 输出：

```text
tick= 45 cell0=3932 fault=NONE  chg=1
tick= 46 cell0=4300 fault=NONE  chg=1
tick= 47 cell0=4300 fault=NONE  chg=1
tick= 48 cell0=4300 fault=OVP   chg=0
tick= 49 cell0=4300 fault=OVP   chg=0
tick= 50 cell0=4300 fault=OVP   chg=0
```

第 46 拍电压就跳到 4300 mV 了，可 `fault` 仍是 `NONE`、充电还开着；到第 **48** 拍才翻成 `OVP` 并把 `chg` 拉成 0。**二拍确认**：46、47 两拍越限先记账，第三拍（48）才动作。因为这里是 1 秒一拍的教学节奏，不是 20 ms。

再看切断对**下一拍**的影响（同一条流水线，第 48 拍动作之后）：

```bash
python3 -c "
import csv
rows=list(csv.DictReader(open('code/firmware/pc-demo-output/samples.csv',encoding='utf-8')))
for r in rows[46:51]: print(f\"tick={r['tick']:>3} 请求={r['requested_a']:>5}A 实际={r['actual_a']:>5}A chg={r['charge_on']}\")
"
```

2026-10-09 输出：

```text
tick= 47 请求=  2.0A 实际=  2.0A chg=1
tick= 48 请求=  2.0A 实际=  2.0A chg=0
tick= 49 请求=  2.0A 实际=  0.0A chg=0
tick= 50 请求=  2.0A 实际=  0.0A chg=0
tick= 51 请求= -2.0A 实际= -2.0A chg=0
```

第 48 拍**动作**（`chg` 翻 0），电流是在第 **49** 拍才被掐掉的。脚本里那句 `allowed = previous["charge_on"] if requested > 0 else previous["discharge_on"]` 就是这件事：一拍里加进来的电流，要看**上一拍**的命令允不允许。保护不是「这一拍说断就断」，执行有它的延迟。

**交**　贴那两段输出，并用一句话说出「动作拍」和「电流归零拍」差了几拍。

**口诀**　去抖看越限，回差看恢复；切断晚一拍。

**今天你解锁了**　你能在逐拍记录上指出「哪一拍做的判决」和「哪一拍执行到位」，而不是把它们当成同一件事。

**短自测**　如果去抖从「二拍确认」改成「一拍就动作」，第 46 拍就断，会有什么代价？

<details>
<summary>先自己答再展开</summary>

噪声会直接变成停机。真实采样里有尖峰和毛刺，单拍判决就等于「谁噪声大谁说了算」——这正是 `protection-debounce.svg` 里那 20 ms 计数的意义：拿时间换掉误动作。代价是响应变慢，所以短路那一档走**另一条**通路（比较器 + 硬件，微秒级），不走这条软件去抖。两档并存，不是一个阈值管所有故障。
</details>

## 第 3 天：C 状态机是真的在跑

**读**　[阶段 3 §3.4](../stages/stage-3-AFE-MCU智能BMS.md) 的四层架构，以及 `code/firmware/README.md`。

**看**　[BMS 主状态机巡游](../circuits/assets/state-machine.svg)。令牌沿初始化、待机、充电、均衡、放电巡游，任意状态下保护触发都直接拉进故障态——今天这条环被真实喂了一遍 100 拍。

**看码**　`code/firmware/bms.c`（226 行）与 `pc_bridge.c`（80 行）：Python 只通过有超时的管道喂数字、读 JSON，**状态机逻辑不复制**。所以「Python 跑通」等于「这份 C 真跑通」。

**跑**（确认它是个能单独跑的 C 程序）：

```bash
python3 -c "
import sys, tempfile, pathlib, subprocess
sys.path.insert(0,'code/firmware')
import pc_demo
exe = pc_demo.build_bridge(pathlib.Path(tempfile.mkdtemp()))
print('exe =', exe.name)
r = subprocess.run([str(exe)], input='4150 4150 4150 4150 2000 250 1 76\n', capture_output=True, text=True)
print(r.stdout.strip())
"
```

2026-10-09 输出：

```text
exe = pc_bridge.exe
{"tick":1,"state":"STANDBY","state_id":1,"fault":"NONE","fault_mask":0,"charge_on":0,"discharge_on":0,"balance_mask":0,"soc_pct":76,"snapshot_valid":0,"snapshot_tick":0,"snapshot_fault":"NONE","snapshot_current_ma":0,"snapshot_cell0_mv":0}
```

一行七个数（四串电压、电流、温度、充电器在不在、SOC）× 一次回车 → 一行 JSON 状态。编译时用的是 `-std=c99 -Wall -Wextra -Werror`：**警告即错误**，所以它编得过这件事本身就是一条断言。

没装 gcc 会怎样（负控，故意给个假编译器）：

```bash

```

2026-10-09 输出（`2>&1` 是为了让那句报错和退出码落在同一段里）：

```text
PC demo failed: 找不到 C 编译器 not-a-compiler；先安装 gcc 并加入 PATH

exit=2
```

**口诀**　Python 搭台，C 唱戏；逻辑只写一份。

**今天你解锁了**　你能把 C 状态机当独立可执行程序喂输入、读输出，而不依赖任何硬件。

**短自测**　为什么这个实验宁可走「编译 + 子进程 + 管道」，也不直接把状态机用 Python 重写一遍？

## 第 4 天：坏一帧，收全 99 帧

**读**　[UART 字节状态机](../circuits/assets/uart-byte-machine.svg) 的图说与 [阶段 5 §5.2](../stages/stage-5-通信与集成.md)：找帧头、收长度、收数据、对 CRC；校验失败要**计数并重新同步**，不能静默丢掉。

**看**　[UART 字节状态机：找帧头、收长度、收数据、对 CRC](../circuits/assets/uart-byte-machine.svg)。字节流逐字节过状态机，坏帧计数后重新同步——今天数它扔了几帧、找回了多少帧。

**跑**：

```bash
python3 -c "
import json, csv
r = json.load(open('code/firmware/pc-demo-output/report.json', encoding='utf-8'))
print('wire.bin =', len(open('code/firmware/pc-demo-output/wire.bin','rb').read()), 'B')
print('received =', r['received_frames'], '| bad_crc =', r['bad_crc'], '| resyncs =', r['resyncs'])
ticks = [int(x['tick']) for x in csv.DictReader(open('code/firmware/pc-demo-output/telemetry.csv', encoding='utf-8'))]
print('tick 1..', ticks[-1], '| missing =', [t for t in range(1,101) if t not in ticks])
"
```

2026-10-09 输出：

```text
wire.bin = 3003 B
received = 99 | bad_crc = 1 | resyncs = 4
tick 1.. 100 | missing = [13]
```

3003 字节发出去，100 帧里坏 1 帧（第 13 帧），收到 99 帧，缺的正是 `[13]`——**一帧都没多、一帧都没少**。

「4 次重新同步」是哪四次？逐字节喂一遍，看它停在哪：

```bash
python3 -c "
import sys
sys.path.insert(0,'code/protocol')
from frames import FrameParser
wire = open('code/firmware/pc-demo-output/wire.bin','rb').read()
p = FrameParser(); prev = 0; marks = []
for i, b in enumerate(wire):
    p.feed(b)
    if p.resyncs != prev: marks.append((i, p.resyncs)); prev = p.resyncs
print('resync 字节下标 =', marks, '| 附近字节 =', [hex(wire[i]) for i,_ in marks])
"
```

2026-10-09 输出：

```text
resync 字节下标 = [(389, 1), (960, 2), (961, 3), (962, 4)] | 附近字节 = ['0x58', '0x0', '0xff', '0x19']
```

四次里，第 389 字节那次是**被扔的第 13 帧**（校验不过，得重新找边界），第 960–962 字节那三次是脚本塞进去的三个垃圾字节 `00 ff 19`——每个都让解析器重新对齐一次，而它每次都追回来了。

`resyncs` 与 `bad_crc` 是两个数，别混：前者是「字节流失去对齐后重新找回边界」的次数，后者是「帧找到了但校验不过」的帧数。4 比 1 不是矛盾，是两次不同性质的事故各记各的账。

**交**　贴上面那段输出，并回答：`missing` 为什么正好是 `[13]` 而不是 `[12]` 或 `[14]`？

**口诀**　坏帧要计数，重同步要停下脚——静默丢数据最贵。

**今天你解锁了**　你能拿一份原始字节流和一份接收日志，逐帧对账，指出哪一帧被扔、为什么扔、后面有没有接上。

**短自测**　脚本弄坏的是「最后一个字节」（CRC 字段），如果改成弄坏负载里的一个字节，最后那 99 帧的结论会不一样吗？

<details>
<summary>先自己答再展开</summary>

不会，结论一样、机制不同：接收端对比的是**整帧**算出来的 CRC，负载改了，CRC 就对不上，同一帧照样被扔。区别在于「谁能发现」——只改 CRC 字段时，如果接收端不重算、只信任帧里的 CRC，就发现不了；改负载而接收端重算，是校验在干活。所以 CRC 必须**重算后比对**，不能「照着抄一遍」。
</details>

## 第 5 天：没有真值也听得见

**读**　[SOC 真实数据专题 §5](../SOC真实数据专题.md) 与 [SOC 五天 Day 5](01-soc五天.md)：新息（残差）$z - h(\hat x)$ 只用到你自己手里的量，不需要参考 SOC。

**看**　[短路保护：微秒级的反射神经](../circuits/assets/short-circuit-timeline.svg)。约 10 A、t=0、约 2 μs 比较器翻转、约 10 μs MOS 关断——时间是示意。今天注入的短路是**采样端的 −31 A**，不是这条微秒级时序，两者别混。

**跑**（恒流段的稳态新息当基线，再看三段注入）：

```bash
python3 -c "
import csv, statistics as st
rows = list(csv.DictReader(open('code/firmware/pc-demo-output/samples.csv', encoding='utf-8')))
inn = lambda r: abs(float(r['innovation_mv']))
steady = st.median(inn(r) for r in rows if r['phase'] in ('charge','discharge'))
print('steady median |innovation| =', round(steady,3), 'mV')
for ph in ('ovp_sensor','short_sensor','hot_sensor'):
    print(ph, 'max =', round(max([inn(r) for r in rows if r['phase']==ph]+[0.0]),1), 'mV')
last = rows[-1]
print('snapshot: valid=%s tick=%s fault=%s cell0=%s mV' % (last['snapshot_valid'],last['snapshot_tick'],last['snapshot_fault'],last['snapshot_cell0_mv']))
"
```

2026-10-09 输出：

```text
steady median |innovation| = 0.219 mV
ovp_sensor max = 71.7 mV
short_sensor max = 585.2 mV
hot_sensor max = 29.2 mV
snapshot: valid=1 tick=48 fault=OVP cell0=4300 mV
```

恒流段新息中位数 **0.219 mV**——正常时模型和采样对得上。三段注入各是 71.7 mV、585.2 mV、29.2 mV，全在百倍量级上喊了出来。过压注入那一段尤其值得看：电压被人为抬到 4300 mV，估算器不知道，新息先叫，保护随后到——**两条独立的线都指向同一个采样**。

还有一次「先来后到」：快照锁存。最后一拍 `snapshot_tick=48`、`snapshot_fault=OVP`。第 48 拍是第一次判出 OVP 的那一拍，后面 52 拍里状态又动过、电压也变过，快照**没有被后来的故障覆盖**——第一现场留住了。

**交**　贴输出，并把四个数写进一句：基线多少、三段各多少倍。再说一遍 `hot_sensor` 那条为什么也要留意（见短自测）。

**口诀**　真值会骗人，残差不会；第一现场要锁住。

**今天你解锁了**　你能在没有参考 SOC 的情况下，用一条残差曲线指出「这一拍采样不对」，并说出证据链到哪一步为止。

**短自测**　温度从 25.0 °C 跳到 65.0 °C，新息只涨到 29.2 mV，为什么**远小于**电压注入那两段？

<details>
<summary>先自己答再展开</summary>

因为**温度不进观测方程**。估算器的 `step(current_a, v_meas, dt_s)` 只看电流和端电压，温度根本不参与，所以温度怎么跳，对新息的直接影响都很小——这 29.2 mV 主要来自温度变化间接带来的模型差异与瞬态，不是观测直接被扰动。这条边界很重要：残差**只对它见过的那两个量**负责。反过来讲，一个只看电压电流的诊断，永远不该声称「我检测到了温度传感器故障」。
</details>

**练完你会怎样**：你能一条命令跑出 100 拍的全链路运行记录，指着逐拍表说出「第几拍判决、第几拍执行、第几帧被扔、哪一拍采样不对」，并知道每一条结论的证据到哪一步为止——因为这里的故障是采样端注入，不是硬件的微秒级反射。
