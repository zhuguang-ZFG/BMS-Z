# 第 18 章 通信：坏一帧，收全 99 帧

::: story 现场
一条 100 帧的遥测流，第 13 帧被故意异或坏一个字节。解析器扔掉它、计数 `bad_crc: 1`，然后靠重同步把后面的 87 帧全部收回——最终 `received_frames: 99`，`resyncs: 4`。

少一帧不是丢数据，是**验收项**。通信的可靠性不是“永远不出错”，而是“出错之后还能不能继续”。
:::

## 18.1 字节流没有帧界

UART/CAN 给你的是一串字节，不是“一条条消息”。解析器必须自己找边界：

```
帧头 → 长度 → 元信息 → 数据 → CRC
```

BMS-Z 的 `frames.py` 用逐字节状态机实现，五条“军规”：

1. **逐字节喂入**：`feed()` 每次收一个字节，状态由缓冲内容与长度决定。
2. **坏帧计数不静默**：长度非法、CRC 错、残帧、重同步分别计数。
3. **垃圾前缀重同步**：保留末尾孤立的 `0xAA`；坏帧只排除当前帧头，余下字节重新扫描。
4. **单字节喂入 + 超时 flush**：`feed` 每次至多返回一帧；帧间超时或流结束要 `flush()`，处理残帧。
5. **物理量换算**：raw16 大端 × 1 mV，单位与端序写在协议里。

## 18.2 为什么“看起来能收”不够

一个常见的错误实现：读到 `0xAA 0x55` 就开始收固定长度，CRC 错了就把整段丢掉。问题是：

- 丢掉的可能包含下一帧的帧头；
- 缺 CRC 的旧帧会吞掉下一帧；
- 长度字段坏了，可能一直等到超时。

BMS-Z 的重同步策略是：**只排除当前坏帧头，余下字节重新扫描**。所以合法帧里出现的 `AA 55`（甚至完整的内嵌好帧）都按载荷保留，不会被误切。

::: principle 一句话
**坏帧要计数，重同步要保守，残帧要 flush。** 通信的鲁棒性，藏在这三个动作里。
:::

## 18.3 端到端保护

CAN 帧可能被截断、重复、乱序；Modbus 轮询可能超时；MQTT 可能断网重连。上层要能判断“这条数据是不是过期了”：

- CRC + 滚动计数器；
- 时间戳/超时；
- 版本号与失效替代值；
- 关键信号双帧冗余。

没有端到端保护，你会遇到“SOC 看起来合法，其实是 3 秒前的值”。

## 18.4 真实协议长什么样

教学帧格式是抽象。真实项目里：

- JK-BMS 的 UART/BLE 帧有固定头、长度、命令、CRC；
- 不同型号/固件的寄存器与缩放可能不同；
- 厂商文档常常缺失，需要抓包 + 已知量对照。

BMS-Z 的阶段 5 把“方言与官话”“老干部 Modbus”“协议侦探”讲得很生动：UART 是商用 BMS 的方言，CAN 是车上的官话，Modbus 是储能世界的老干部——慢，但哪儿都认得它。

::: trap 坑
把 `read()` 的分块当成“帧边界”。串口一次 `read` 可能给你半帧，也可能给你三帧；只有超时或显式长度才能定界。
:::

## 练习

1. 串口一次 `read()` 给你“三帧半”，解析器应当输出什么？帧定界只能依赖哪两类信息？
2. 为什么“收到 0xAA 0x55 就收固定长度、CRC 错就整段丢”的实现会连锁丢帧？用 18.2 列的三个问题说明。
3. 给 BMS-Z `frames.py` 的五条军规，每条写一句可执行的测试方法。
