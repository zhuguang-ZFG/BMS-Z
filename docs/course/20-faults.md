# 20 · 用故障回放找出最早失守的位置

先修：[第 19 课](19-loop.md)的逐拍日志。完成本课，你能区分异常出现、保护判决、反馈动作和后续故障四个时刻。

## 从第一处变化查起

最终报告出现 `ACTUATOR_STUCK` 时，不应先改欠压阈值。先回看输入：电压从哪一拍越线；再看断开命令；最后比较反馈。一个系统可能先正确发现欠压，随后因执行器不动作又发现第二个故障。只保存最后一个故障码，会丢掉前因。

运行场景时只替换命令中的名称，每个场景用自己的输出目录。先在纸上预测，再查看实际结果：

```sh
python code/course/project.py --scenario feedback --work .tmp-my-bms.py --out .tmp-my-run/feedback
```

| 场景 | 刻意改变什么 | 应检查的差别 |
|---|---|---|
| `nominal` | 无故障 | 全程允许，SOC 按电流更新 |
| `spike` | 0.30 s 只低一拍 | 0.40 s 恢复，不累计成欠压 |
| `undervoltage` | 0.30 s 起持续欠压 | 0.50 s 命令断开，0.60 s 反馈打开 |
| `stale` | 0.60 s 起重复旧采样 | 质量无效并禁止输出，SOC 质量失效 |
| `feedback` | 欠压后反馈始终闭合 | 命令断开后仍流电，0.70 s 追加卡住故障 |
| `timeout` | 远程接收时间停止更新，采样继续 | 通信过期时禁止输出，采样质量仍可能有效 |
| `transfer` | 容量、周期与欠压单节改变 | 留给下一课独立迁移 |

这些场景都是人为注入的数据，名字不代表故障原因已经在实物上得到确认。真实旧数据可能来自采样停止、队列堵塞或时钟错误，需要进一步证据区分。

## 两种“没有新数据”分开记

`stale` 的问题发生在电池测量链：同一采样时间被重复使用，即使数值很正常，也不能更新为新的观察。控制器要求时间递增；重复或缺段会让 SOC 可信标记失效，后续出现新样本也不自动假装缺段已经补齐。

`timeout` 则让测量继续正常，只停止远程消息。项目使用接收年龄 **≤0.30 s（含端点）** 的教学通信规则，首次超过时锁存 `COMM_TIMEOUT`。这条通信等待时间不用于延迟本地过压或样本无效保护。

## 用时间差证明反馈超时

`feedback` 中 0.50 s 发出断开命令，0.60 s 反馈仍闭合，此时只过了 0.10 s；到 0.70 s 仍闭合，才达到 0.20 s 教学上限。应同时保留 `UV` 和 `ACTUATOR_STUCK`。从首个欠压点到卡住故障共 0.40 s，其中前 0.20 s 是欠压确认，后 0.20 s 是执行器等待，不能全部称为“软件没反应”。

## 合上例子再做

比较 `stale` 与 `timeout` 的首次禁止输出行，写出 `sample_valid`、`remote_fresh`、`soc_valid` 和故障名。若反馈在断开命令后 0.19 s 已打开，是否仍应报告超时卡住？说明仅凭 CSV 不能判定的一项硬件原因。
