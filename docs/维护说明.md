# 维护说明

> **本篇你会学到**　外链巡检为什么有 16 个域名要人手点，CI 又守着哪几件事，发一版要留下哪四处凭据，发帖表为什么会静默套不上。
> **预计用时**　维护者月度复查、发版收口时用。
> **前置**　[共建任务板](共建任务板.md) 的 T2。

外链由 [lychee 月度巡检](../.github/workflows/links.yml)（反爬站点按 `.lychee.toml` 配置豁免）；代码测试、ruff 静态检查与文档相对链接/SVG 计数随 PR 运行，文档站的构建与产物对账也随 PR 运行（tests.yml 的 site-build job：构建挂了、产物有死链、某页没人链到、正文有的词搜索翻不到，在 PR 上就拦下，不等合并）。外链这道门是**两轮制**：GitHub 的 blob HTML 路由会分钟级抖 503/504——判据没错，缺的是抗性——所以第 1 轮报红就等 180 s 复跑一轮，**两轮都红才判红**，第 1 轮绿则第 2 轮整个跳过。立这条的依据是 2026-10-09 两次 push 的 links 分别报 24 条与 25 条错误（各自 3301/3305 条总数、0 超时），全是 `github.com/.../blob/main/...` 自链的 503/504、0 条 404，其中不少文件那一轮根本没改；同一批 URL 本机立刻重放，16 条里 15 条仍 503/504，而同内容的 `raw.` 域名、同文件的 `/blame/` 路由与 Pages 站全 200，`/api/v2/summary.json` 报 Operational。`.lychee.toml` 的 accept 表一个字没动：5xx 依然算失败，只是不给一次瞬时抖动单独投票权。发现错误欢迎提 Issue。

文档站（[在线版](https://zhuguang-zfg.github.io/BMS-Z/)）由 [deploy-pages workflow](../.github/workflows/deploy-pages.yml) 发布：push 到 main 触发 VitePress 构建，构建完先跑 [check_pages.py](../.github/scripts/check_pages.py) 对产物逐条对账站内链接与锚点，不过不发版——源码侧的检查器看不见产物，这道门只在部署前。正文写法不为站点让步：跨出 docs/ 的相对链接、目录链接、docs 内的源文件链接由渲染期插件（[escaping-links.ts](.vitepress/escaping-links.ts)）改写成 GitHub URL，动画与照片（circuits/assets/）按原相对路径拷进产物。改站点时三处单一来源要一起看：[site-assets.json](.vitepress/site-assets.json)（哪些仓库根文件由站点托管，值不带 base，自己写了 base 会被 VitePress 再补一次变双写）、[base.ts](.vitepress/base.ts)（`/BMS-Z/` 前缀，config 与首页数据共用）、config.mts 的 githubSlugify——它与 check_docs.py 的 slug 规则是双胞胎，改一边另一边必须同步，锚点对账靠这个对上。

皮肤只有一处：[.vitepress/theme/index.ts](.vitepress/theme/index.ts) 继承默认主题并挂上 [custom.css](.vitepress/theme/custom.css)，全站没有第二份 CSS，也没有页面内 `<style>`（首页的 `stage-list`、`learning-cockpit`、`learning-ladder`、`learning-step`、`practice-*` 与 `pack-*` 结构类都只在这份 CSS 里认领）。2026-10 起「一处」多了一半：这个入口还注册了本站第一处运行时 JS——`v-bms-check` 指令，让验收清单的勾选活过刷新。它只写 DOM property 不写 attribute（写 attribute 会让服务端渲染与客户端状态打架）；页键由渲染插件（[checklist-render.ts](.vitepress/checklist-render.ts)）在构建期把 `state.env.relativePath` 戳进 `data-bms-page`，控件与首页电池组两边同源取键——拿 `location.pathname` 反推会在中文文件名上失配（百分号编码对原文中文）。条目身份与框数对账的唯一口径在 [checklist.ts](.vitepress/checklist.ts)，改清单形状要连着它一起改。首页电池组也吃这一份：格子的条目与键由 [index.data.ts](index.data.ts) 构建期现算（不写死数字，产物里 57 个 `data-bms-key` 与首页那 57 个键实测逐一对得上），读数口径钉死为**已采样各格完成度取最小**——木桶，平均只作为「安慰值」并列显示，因为平均恰好会把漏检那一节藏起来；一格从没被勾过算「未采样」，既不参与取最小也不画 0% 的水（0% 是「做了没做对」，未采样是「根本没有读数」，工程上两件事）。毕业那一格读 `bms-resources.md` 的精通自检清单——stage-6 正文自己一条 `- [ ]` 都没有，照正文算就是一格永远钉在零的电芯。三条口径写在这份 CSS 的头注释：颜色一律取 `--vp-c-*`，唯一例外是跟 150 张动画同源的 Primer 强调蓝（浅 `#0969da`、深 `#4493f8`）——注意 `--vp-c-brand-3` 是**主按钮的底色**不是「更亮的蓝」，白字压在上面实测浅底 5.19:1、深底 4.63:1 才过 AA，图省事填 `#54aeff` 会掉到 2.37:1；不引外部字体，中文走本机族（默认主题一个中文字族都没写）；装饰只做边线、留白、圆角与一层浅影。改皮肤要在浏览器里量对比度与 computed style，别照截图凭感觉——`.VPFeature` 这类组件是 scoped 样式（`.VPFeature[data-v-…]`，0,2,0），单写一个类打不动它，首页卡片必须写 `.VPHome .VPFeature`。首屏 hero 右侧**故意留空**：frontmatter 的 hero 图不带 `width`/`height`，会引入首屏位移，而 `check_pages.py` 的宽高那道门防的正是这件事；`image.html` 写法又必须把 `/BMS-Z/` 前缀写死，破掉 [base.ts](.vitepress/base.ts) 的单一来源。所以路线动画放正文，走 markdown 管线拿宽高与懒加载。

深色模式有两处坑，都用实测钉过。**验深色要用 `npm run docs:preview`，不能用 `docs:dev`**：给 `<html>` 挂 `dark` 类的防闪烁脚本 `check-dark-mode`（读 `vitepress-theme-appearance`，没有显式选择时按系统 `prefers-color-scheme` 判定）只出现在构建产物里——同一份首页，dev 的 HTML 里 grep 是 0 次、`dist/` 里 1 次。在 dev 上把 `prefers-color-scheme` 模拟成深色，`<html>` 始终是空类、正文底色始终是 `rgb(255,255,255)`，很容易误判成皮肤坏了（本轮就误判过一次）。第二处：**150 张动画是 `<img>` 引进来的，SVG 内部那句 `@media (prefers-color-scheme: dark)` 只听操作系统，读不到页面的 `html.dark` 类**，所以「系统深色 + 手动切到浅色」这一档必然错配：实测页面底色 `rgb(255,255,255)`，而 `coulomb-counting.svg` 的 60×60 采样里 3306/3600 个像素是暗的（均值亮度 33），白页里嵌一张黑底图。要彻底消掉只有一行 `appearance: 'force-auto'`，代价是导航栏那个手动开关消失；把 SVG 内联进 HTML 倒是能吃 `html.dark`，但那要废掉 config 里「始终以真实 .svg 出站点」这条，SMIL 与在 GitHub 上打开的一致性就没了，150 张一起内联还会把 HTML 撑大——不值。深色底实测对比：正文 12.81:1、链接 5.54:1（压在引用块底 `rgb(32,33,39)` 上 5.18:1）、行内代码压在 `rgba(101,117,133,.16)` 上 4.67:1、表头 5.6:1。

同一道 [check_pages.py](../.github/scripts/check_pages.py) 还做反向对账：产物里哪一页没有任何别的页面链到它，就报「孤儿」。侧栏的「其他」是兜底不是归宿——新文件落进那里，说明归组表（sidebar.ts 的 ROOT_GROUPS）该给它加一条了。闸门与部署分两处：site-build job 在 [tests.yml](../.github/workflows/tests.yml) 里（PR 与 push 都跑），deploy-pages.yml 只管发（只有 main 能进）。同一份 dist 检查跑两次是有意的，PR 上红一次好过合并后部署红、线上停更。本地手动复跑这道门照 CI 那条命令写，**不要补 `--base /BMS-Z/`**：Git Bash 会把以 `/` 开头的实参改写成 `C:/Program Files/Git/BMS-Z/`，产物页脚对账随即整片假红（实测报成「上一篇要写 `C:/Program Files/Git/BMS-Z/擂台.html`，实际是 `/BMS-Z/擂台.html`」，退 1 却一条真问题都没有）。脚本的 `--base` 默认值本来就是 `/BMS-Z/`，省略即对；确实要显式带，就加 `MSYS_NO_PATHCONV=1` 压掉改写。

公式沿用正文既有的 `$…$` 与 `$$…$$`（和 GitHub 同一套写法），站点侧靠 `markdown.math` 渲染，需要 dev 依赖 `markdown-it-mathjax3`。它经 speech-rule-engine 把 `@xmldom/xmldom` 钉死在 0.9.10（13 条高危公告），所以 package.json 用 `overrides` 抬到 0.9.12——换数学库或升依赖时记得一起复核这一条。数学块必须独占一行：写在句子中间的 `$$…$$` 块级规则不认，全站唯一一处（阶段 4 §4.1 的「原理」行）已按仓库既有约定改成单 `$…$`。

分享卡片与收录靠三份产物级配置，绝对地址都从 [base.ts](.vitepress/base.ts) 的 `SITE_ORIGIN + BASE` 拼，只这一份。sitemap 的 hostname **必须带尾斜杠**：VitePress 内部用 `new URL(item, hostname)` 解析，hostname 少个尾斜杠会把整段 base 丢掉（实测产出 `https://host/AI陪练卡.html`，正确是 `https://host/BMS-Z/AI陪练卡.html`）。每篇的 og 摘要按「frontmatter > 正文那句『本篇你会学到』（59 篇里 27 篇有）> 站点简介」取，不新编文案。站点图标在 `docs/public/favicon.svg`（VitePress 原样拷到 dist 根），画的是仓库自己那套色板：底 `#0d1117`、线 `#e6edf3`、闪电 `#3fb950`。每篇页面的预览图暂时借 GitHub 的仓库社交预览（`opengraph.githubassets.com`，对任何公开仓库稳定出图）；站点自己那张 1280×640 封面只挂在门户 HTML 的 `og:image` 上，由 `tools/gen_social_card.py` 画，理由见下面「张数」那段。

站内搜索是这个站最容易坏、又最不会报警的一环，所以它有自己的门禁：[check_search.mjs](../.github/scripts/check_search.mjs)。MiniSearch 默认只在空白和标点处切词，中文两字之间这两样都没有，整句会变成一个词条——切二元组之前那一次真值表实测：「油箱」正文 9 页有、默认切法只翻到 3 页，「采样」38 页只翻到 28 页。修法是把汉字串切成二元组（[cjk-search.ts](.vitepress/cjk-search.ts)），非中文保持默认切法不变，改完门禁里那 8 个词全部翻满（2026-10-07 复跑是 10/10、39/39——正文长一页，真值就跟着变一页，这两个数由门禁现算，不是写死的期望值）。为什么不用 `Intl.Segmenter` 分词：词条在 CI 的 Node 里建、查询串在访客浏览器里切，两端必须切出同一批词，而 Segmenter 的中文词库依赖浏览器 ICU 数据，缺数据时整串返回，查询和索引立刻对不上；二元组是纯字符串运算，两端必然一致。代价是词表里混进「箱慢」「在的」这类跨词二元组，所以它是召回优先的写法：拿一句胡说八道的话去搜也能出一串命中，把噪声压下去靠的是排序。门禁因此除了「正文有就必须翻到」，还断言排名第一的命中页正文里真的有这个词。检索参数保持 MiniSearch 默认的 `combineWith: 'or'`，不改成 `'and'`：查询一旦跨过词边界，就会出现「衡怎」这种索引里根本不存在的二元组，实测「被动均衡怎么发热」在 and 下 0 条命中、or 下第一篇就是详解③的被动均衡节。这条链路有个隐藏的坑：VitePress 把 `themeConfig` 里函数的**源码**塞进每页站点数据、浏览器再 `new Function` 还原，源码引用的模块级变量带不过去——所以 `tokenizeCjk` 必须完全自包含，门禁会把 HTML 里那段副本取出来与模块实现逐条比对。代价记在账上：索引从 1018KB 涨到 2176KB（gzip 524KB），它是搜索框组件的动态 chunk，只有访客真的打开搜索才下载。真值不是写死的期望条数，而是从 docs/ 正文按标题切段现算（首个标题之前的段落不进索引，公式渲染成 SVG 也不算）——这道口径自己踩过一次雷：剥 frontmatter 的正则写成 `^---[\s\S]*?^---`，碰上没有 frontmatter 的文件，就把正文里两条分隔线之间的一大段一起吃掉了，阶段 4 剥完只剩 672 个字符能算数，真值表静默缩水，搜索漏了多少页都查不出来；现在只在文件第一行确实是 `---` 时才剥。加词请加正文里的句中词，只在标题开头的词靠前缀匹配就能侥幸命中，证明不了什么。

图片这一侧同理：一页最多 36 张图、合计 1493KB（阶段 6），实拍照片单张最大 457KB，浏览器一解析到 `<img>` 就全下下来，手机上翻开一篇文章的首屏要为几十张永远看不到的图买单。[lazy-images.ts](.vitepress/lazy-images.ts) 在渲染期给每页除首图外的图加 `loading="lazy"`（首图留着别拖慢首屏最大内容绘制），并按源文件真实像素补 `width`/`height`——SVG 读 viewBox、JPEG 读 SOF 段、PNG 读 IHDR 头。两件事必须一起做：懒加载只是把下载推迟，没有宽高就会在图片落地那一刻把正文顶开，动画正看着会跳；主题样式是 `img{max-width:100%;height:auto}`，浏览器会用这两个属性先把位置留好（实测未加载的懒加载图已占住 346px 高）。读不出尺寸的就只加懒加载，绝不写错的尺寸——外链视频封面 9 张没有宽高是有意的。改前改后的数：全站正文 209 张图，逐页加总全量 6374KB，现在首屏必载 673KB。产物侧一起对账：[check_pages.py](../.github/scripts/check_pages.py) 现在也查 `<img>`——src 必须命中 dist 里的真实文件、除每页首图外必须懒加载、站内图必须带宽高。

同一处对账顺带抓出一个迁移遗留：仓库根那张 [BMS学习路径.html](../BMS学习路径.html) 是原样拷进 dist 的，它的图片引用按仓库根写（`src="docs/circuits/assets/…"`，GitHub 网页端和本地双击都靠这个），而站点根是 docs/，Jekyll 时代两者重合、换 VitePress 后这句就指到 `/BMS-Z/docs/…` 404 了（线上实测：带 docs 前缀 404、不带 200）。`<img>` 不像 `![](...)` 会被 Vite 接管解析，构建一声不响。现在 [copy-site-assets.mjs](.vitepress/copy-site-assets.mjs) 在拷 HTML 时去掉这层前缀，源文件保持 GitHub 那边能点的写法，构建日志会打出改写了几处。

- **标签指向**：`git for-each-ref --format='%(refname:short) %(objecttype) %(objectname) %(*objectname)' refs/tags`。附注标签（v1.1.0、v1.3.0）有两个 sha——标签对象和它指向的提交；轻量标签只有提交那一个。两种写法在表里不混用，因为 `%(objectname)` 对附注标签给的不是提交号。
- **发布时间**：`gh release list --json tagName,publishedAt`。认 `publishedAt`，不是 `createdAt`——v1.3.0 这两格差一分十八秒（草稿转正式之间），只有 `publishedAt` 是读者看到的时刻。
- **收口提交**：把 Unreleased 并进版本节、把各处「标签待打」改成已发布、补 compare 落款的那一次提交。它必须在标签**之后**才进 `main`：`releases/tag/vX.Y.Z` 和 `[1.3.0]: …/compare/v1.2.0...v1.3.0` 这类落款写早了就是死链，links 巡检当场变红。从 v1.4.0 起它还得排在 Release 之后——同一次提交要给表补那一行，而发布时间那一列必须是真实的 `publishedAt`（口径见下面那段）。并条目时节首「共 N 条 / 覆盖 M 个提交」用 `python3 tools/release_stats.py --from v1.2.0 --to v1.3.0` 现数，别沿用两天前的数——1.3.0 从草案到定版就是 41 条/30 个提交漂到 44 条/33 个提交，而定版那一句现在能被这条命令原样复现。同一次提交还要把读者能看到的三处门面一起升版：README 的「📣 最近更新」折叠块、门户 [BMS学习路径.html](../BMS学习路径.html) 的卡片、[更新动态](更新动态.md) 的导读句。**并条一条都不能丢**：真值侧会从那一次提交往前逐份快照读 `git show <rev>:CHANGELOG.md`，窗口里每一次 `## [Unreleased]` 出现过的条目，都必须能在收口提交的版本节里找到——认前 32 个字，所以收口时把条目的数改成定版值（1.3.0 那条「当时实测 30 个提交」就是这么重写的）门不拦，改开头才拦，因为开头一变就是这条被合并或被换掉的样子。v1.3.0 实测：窗口 4 份快照、Unreleased 去重 44 条、`## [1.3.0]` 节 44 条，一条不差。
- **核验**：收口提交上三条 workflow 的 run 号，加一次线上点开。绿徽章本身不算证据：外链要确认新链接真被 runner 抓到过，就对一下同一分支前后两次 links 的 `Total / Successful / Timeouts / Errors` 四格。v1.3.0 那次是 3061/3023/0/0（`94a58bf`，标签还没落地）→ 3064/3026/0/0（`e298104`），总量与成功各 +3、超时与报错仍是 0。这四格只对量级，不点名具体哪几条：本机按同一 glob 手工数那批新增外链是 +4 处，而 `4012d6d` 一处外链都没加、日志仍是 3065/3027——代码里的 URL 剥不剥、重复 URL 算几次，两边规则本就不同。要对到逐条，得给 lychee 加 `--dump` 再比输出。

标签和 Release 是共享且难回滚的状态，版本号与打标签的时机由维护者确认后再动；「继续」「下一步」这类话都不算这个确认。

里的历史正文。真值这半不进 CI：`actions/checkout@v7` 的 `fetch-depth` 默认是 1，而仓库三个 workflow 里那 7 处 checkout 都没改它，runner 上根本数不到标签、也取不到历史里的 CHANGELOG 正文，硬要比就是把表里每一行都判成假红灯；本机缺 git 或 gh 时记 SKIP 真值侧还要对 CHANGELOG 节首那句数（`check_release_counts()`，跟着 `--release-truth` 一起跑；其中「共 N 条」那一半自本轮起拆到 CI 侧，见下一段）：「共 N 条」要等于那一节里 `- ` 开头的行数，「覆盖 `vX` 之后 M 个提交」要等于 `git rev-list --count vX..vY`，括号里的 PR 区间要等于 `git log --format=%s` 末尾 `(#N)` 现数出来的最小号、最大号与去重个数，「加 P 个直接提交」要等于 M 减去带 PR 号的提交数。那句由 `python3 tools/release_stats.py --from v1.2.0 --to v1.3.0` 生成，工具和门各数一遍再对：1.3.0 定版那句的五个数（44 条、33 个提交、PR #25–#42、共 18 个、加 15 个直接提交）工具逐个复现，措辞上工具只打主干，定版那句多一个「的」和前置分句（正则 `之后的?` 两种都认）；没写这句话的 1.1.0→1.2.0 也能被工具数出 30 个提交、PR #1–#24 共 23 个、加 7 个直接提交——数不是抄进代码的。工具在区间里没有带 PR 号的提交时给另一种说法（「没有带 PR 号的提交，加 M 个直接提交」），两种句式门都判，否则「这一版全是直接提交」的那句正好漏在门外。三种情况记跳过不判红：节首根本没写那句（1.0.0–1.2.0 是收口流程定下来之前的账，不追旧账）、区间两头任一标签本地取不到（草案先写节首、标签后落地是正常状态，缺的是取证条件）、`git` 命令本身失败；Unreleased 里写什么都不判，那一节还没定稿。七道端到端变异报红（条目 44→45、提交 33→30、PR 个数 18→17、区间终点 #42→#41、直接提交 15→14、基线换成 `v1.1.0`、1.3.0 明明有 PR 却写成「没有带 PR 号的提交」），另有五道拿真实历史区间做的单元变异报红（`v1.0.0..v1.1.0` 的直接提交 18→17 与总数 18→19、`v1.1.0..v1.2.0` 的 PR 终点 #24→#23 与直接提交 7→8、给 1.3.0 塞一句假称没有 PR），照抄工具数的两格放行、缺标签的三种记跳过。这七加五道全部当场 assert 正则确实匹配上了——同一轮探针第一次跑就是因为句里少写一个 `v`，让两格「无问题」变成空跑，绿色本身不算证据。

条目数这一半其实**不要 git**，可它原先跟着 `--release-truth` 一起跑，等于只在本地比：有人把 1.3.0 节首的「共 44 条」抄成 45，CI 一路放行，错数直接上线——而这一节数的是本版做了多少件事，读者第一眼看到的就是它。所以把那一半拆成 CI 侧 `check_changelog_counts()`：拿 `changelog_count_claims()` 现算每节「节首写的条数 / 本节 `- ` 开头的行数」，成功行把逐节的数一起打出来，免得绿了看不出比过谁；`check_release_counts()` 里那段重复实现删掉，只留要 git 的后一半。「覆盖 `vX` 之后 M 个提交」与括号里的 PR 区间照旧归本地第十一步——runner 上 `actions/checkout` 默认 `fetch-depth: 1`，数不到标签，同一节里 `check_runner_no_tags()` 守的就是这句根据。**十例全部符合预期**（同一套 `try/finally` 按字节还原，跑完 `CHANGELOG.md` 的 sha 与起手值逐字节一致）：报红四道——1.3.0 节首「共 44 条」抄成 45、往那一节加一条条目而节首不动、从那一节删一条条目而节首不动（三道红信都落在 `CHANGELOG 1.3.0: 节首写「共 45 条」，这一节实际 44 条（数的是本节 `- ` 开头的行）`），第四道是拿同一笔变异改跑本地 `--release-truth`：红信仍是这一句，而不是往下走到真值比对——证明删掉本地那半之后，本地门照样管这件事，也没有两道门各报一遍。反向对照六道保持绿——现状、往 **Unreleased** 加一条条目（新门只读 `## [X.Y.Z]` 那些节，Unreleased 是下一版的账本，还没定稿）、删掉 **1.2.0** 的一条条目（那一节没写节首那句，属于「数没写就不判」）、把 1.3.0 的节首那句整句摘掉、只把「之后的 33 个提交」改成 99（那一半要 git，CI 侧明确不管，别把它当漏）、以及把「共 44 条」改写成「合计 44 条」。最后一道是新门与 `check_release_wording()` 共有的**已知宽口子**，写在这里而不是当场修掉：门对正则认不出的写法一律放行，凭的是那句由 `tools/release_stats.py` 生成、而工具与门的措辞由 round-trip 门钉住——真要换说法得两边一起改，只改 CHANGELOG 会让这一格脱离对账。

收口那一次还有两个方向此前没有任何东西守着，v1.4.0 起草时才发现。**往下**：条目是「搬」进版本节，不是「复制」一份进去——`check_release_record()` 只比小节集合与落款集合，同一条目在 `## [Unreleased]` 和 `## [1.4.0]` 各留一份时两边照样自洽；而从这一版起 Unreleased 不再是草稿堆，它是下一版的账本，重复一条就把下一版的「共 N 条」变成永远数不清的账。新增 CI 侧 `check_release_archive()`：Unreleased 与表里最新那一版的小节，条目开头前 32 字（与并条同一口径）撞车就红。**往上**：Release 正文末尾把读者指向 [更新动态](更新动态.md)，可那一页「本页目录」的分组行没人对账——`check_latest_claims()` 只看带「这批已经发布」字样的导读句，分组行不在它的锚点里。新增 CI 侧 `check_release_dynamic()`：表里最新那一版必须在本页目录有一个 `**X.Y.Z（……）**` 分组，分组行里出现的日期要等于表里的发布日，组下至少留一条小节链接，否则算「分组成了空标签」。同一道门当天就扩到**每一个**分组，不留「只测最新一版」的洞：分组写出的版本号必须真在发布记录表里（否则红在「读者视角走在凭据前面，等于宣布一个没发过的版本」）、写了日期就要等于表里那一版的发布日、组下不许是空标签、同一版不许有两条分组行。仍然放宽的两处：历史分组可以整组缺席（这一页的口径是「最新这批 + 上一批」，v1.0.0／v1.1.0 本来就没组），历史分组也可以不写日期——当年的写法不改写，与 `check_latest_claims` 同一口径。**十三例全部符合预期**：报红六道——1.3.0 节首那句之后复制一条 Unreleased 的整句（红在「收口漏了『搬』这一步」）、删掉 1.3.0 的分组行、分组行日期抄成 →（维护者确认）建 Release → **一次收口提交做完「归档 + 表行 + compare 落款 + 三处门面 + 更新动态分组」**（表那行的收口提交与核验两列先写「未记录」，只有这两列允许）→ CI 三绿后单独一次提交回填收口提交与三个 run 号。代价是标签指向的那个提交里，这批条目还挂在 `## [Unreleased]`——那不是漏；而标签已推、表行未落地这段时间里 Release 的 diff 也停在标签上。本机实测的三个数是分开的：`git show v1.4.0:CHANGELOG.md` 里 `## [Unreleased]` 是 25 条（这一格被标签钉住，永远不再变），`git rev-list --count v1.3.0..v1.4.0` 是 31（同样被标签钉住），而 `git rev-list --count v1.4.0..HEAD` 和 Unreleased 的条数**每落一个提交就涨一**——所以这一句不钉后两者的现值，要复现就跑这三条命令。计数门 `check_release_counts()` 取的是同一对窗口（条目数从那一节的 `- ` 行——这一半现在由 CI 侧 `check_changelog_counts()` 跑，见上一段；提交数从 `git rev-list --count`），不会把这事判成对不上。**别为了让它们「对齐」把 M 改成数到 HEAD**：那会把收口与回填两次记账提交也算成这一版的成果。

数和措辞还要再一道门，因为工具与门是**两套实现**，而门对「正则认不出的那句」是静默放行：工具哪天改了措辞、或门哪天收紧了正则，工具打的句子就从此没人对账，门照绿、覆盖归零。CI 侧新增 `check_release_wording()`，它不在自己这边重写模板，而是把 `tools/release_stats.py` 当模块读进来，用工具自己的 `sentence()` 拼出两种句式，再要求：各自的正则命中、五个数**原样 round-trip** 回来、两种句式**互不认领**（一种被另一种也认了就算顶包）、手写那种带「的」的写法仍被认（正则 `之后的?` 是为已发布的小节留的，收紧它就把 1.3.0 判成「没写数」）。本地真值侧再加一格：`release_stats_line()` 把工具当子进程跑一遍，拿门的正则解析它打的那句，与节首那组的五个数逐个比——不同就报「两套实现分家」；工具按设计拒绝（本地缺标签，退出码 2）记跳过，工具抛 traceback 判红「跑崩了，这一格的数没跟它对过」，坏掉的门不许冒充缺证据。六道变异各跑两种模式，最有价值的是归属差别：把正则从 `之后的?` 收紧成 `之后`（M3）**只有 CI 红，`--release-truth` 照样绿**——那正好是覆盖静默归零的形态，所以措辞门必须在 CI；反过来把工具的 `direct = total - len(prs)` 写成 `direct = total`（M5）只有真值侧红，CI 的措辞门不管数怎么算出来的。两道门各守一半，红信各自指名「认不出 / 读回别的数 / 互相顶包 / 不再认「的」 / 两套实现分家」。另有一道反向对照：让工具跑不出来，真值侧只记跳过。这一轮也更正了上一轮的过度断言——原先写「工具输出与定版那句一字不差」，实测差一个「的」与前置分句，现在按「五个数逐个相等、措辞主干相同」的口径写。

上面那句「runner 上根本数不到标签」是这两道真值门不进 CI 的**根据**，而根据本身也会坏，所以再加一道门守它（`check_runner_no_tags()`，同在 CI 侧）：正文里「仓库三个 workflow 里那 7 处 checkout」这两个数从 `.github/workflows/` 现读对账（中文数字和阿拉伯数字都认），并且任何一处 `actions/checkout` 显式写了不等于 1 的 `fetch-depth` 就报红。设了 `fetch-depth` 不一定就让标签数得到了，但这句话失去依据的那一刻，「为什么不进 CI」必须重新实测、重新判断，而不是让文档继续引用一个不再成立的理由——所以红信的措辞是「先实测、再决定搬不搬、最后改正文」。这条门也认 `- name:` + `uses:` 的两行式写法：拆行不该让处数凭空少一处，反倒把正文里正确的数字判成错。上线时五道变异报红（workflow 个数写错、checkout 处数写错、一行式塞 `fetch-depth: 0`、把那句理由整句删掉、两行式塞 `fetch-depth: 0`），三道反向对照不报（句尾换个说法但两个数仍对、checkout 拆成两行式仍数得到 7 处、显式 `fetch-depth: 1` 与默认同值）。

表里最新那一版还要往读者能看到的地方抄：README 的「📣 最近更新」折叠块、门户 [BMS学习路径.html](../BMS学习路径.html) 的卡片、[更新动态](更新动态.md) 的导读句。这三处原先没有任何守卫——发新版时只改了 CHANGELOG 与更新动态，README 胶囊和首页卡片会静默停在旧版号，而读者第一眼看到的就是它。现在 `check_latest_claims()` 把它们对回表：那句里链到 `releases/tag/…` 的**链接文字与 URL 两个数**都要等于表里版本号最大的那行，同一句里出现的日期要等于表里的发布日。只管宣布版本的那一处：正文里「`v1.2.0` 之后实测 33 个提交」这类历史基线不追，同句里写也不误伤；徽章和导航条那种带「最近更新」四个字却没有版本号的行也不管。但那句必须留一条指向 Release 标签的链接——把链接摘掉，「最新版本」就退成一个没人能对账的说法，门会红。这条门顺带还守住了另一件事：v1.4.0 还没发就写进门面会当场红，因为表里最新仍是 v1.3.0，而 `releases/tag/v1.4.0` 那时本来就是死链。上线时五道变异报红（README 整句停在旧版、只升 URL 不升文字的半改、门户卡片日期抄错、更新动态导读句日期抄错、把 Release 链接摘掉），四道反向对照不报（历史段换版本号、锚点句里补写 v1.2.0 基线、同文件另加一条不带版本号的「最近更新」行、句尾换说法而版本与日期仍对）。

本地门自己的清单有**四处抄本**：两份门脚本各自吐出的步骤标签、两份脚本头注释里点名的「只在本地跑」名单、CONTRIBUTING 的箭头串，以及那句「前八步／后五步／这五样」。上一轮加第十三步「仓库简介对账」就是把这三处抄本人工对齐一遍——少改一处不会有任何东西变红，因为清单本身在门外，而它是「加门要改哪几处」的唯一答案。现在 CI 侧 `check_local_gate_lists()` 拿**脚本实际吐出的标签**当真值，把四处都对回同一份：只认带 PASS 的那一行，所以 `python 解释器` 那种只在解释器缺失时冒出来的 FAIL-only 伪标签不算一步，同一步吐两次 PASS 也算错（一个名字出现两遍就没法比顺序）；头注释只扫脚本开头的注释块，函数体里写 `「××对账」` 不算点名；本地专属那几道必须正好是清单的**尾部**，不然「后 M 步」这个说法本身就不成立；箭头串的名字要逐字照抄脚本，散文式的「固件 gcc 编译+运行」「算法对比冒烟」「擂台基线」都不算同一步（CONTRIBUTING 已按字面改过，PR 模板那句也跟着统一）；前／后两个数由 `总步数 − 本地道数` 现算，且必须写在箭头串同一行，写别处门读不到就点名。顺带这门逮到一类从更早的表数推出来的错账：凡是「第 N 步「××对账」」的序号都要等于脚本把它吐在第几步——发布记录对账是**第十一**步、分类真值对账第十二、仓库简介对账第十三，而 CHANGELOG 三处与本页一处写的第九、十、十一全偏小了，CONTRIBUTING 那句「脚本一跑第九步当场以 traceback 收场」也是同一笔账，六处一起改。两种情况明确**不报**，都进了反向对照：不带名字的「第九步」无从对账，已发布小节里的序号不改写（同动画张数那道门对历史条目的口径）。上线 19 例，`try/finally` 按字节还原、五份文件 sha 逐个核对一致：**14 道变异全部非零退出**——两份脚本的标签分家、同一步吐两次 PASS、头注释少点名／多点名／调顺序／五道全去掉书名号（名单捞空）、箭头串改回散文别名、锚点句「本地门全绿再推」换说法（正则捞空）、前八步与后五步与这五样各挪一个数、本页的十三退回十一、CONTRIBUTING 点名一个清单里不存在的名，以及最要紧的那道端到端：只往两份脚本各加一步、三处文档都不动，一次报出三条（箭头串少一步、头注释尾部对不上、前八步该是前九步）。**反向对照五道保持绿**：现状、无名的「第十一步」、往已发布的 1.3.0 小节塞一个错序号、函数体注释里写一个 `「不存在的门对账」`、把 `.ps1` 的 BOM 摘掉。最后一道是本轮修掉的真 bug：`.ps1` 必须存成 UTF-8 with BOM（Windows PowerShell 5.1 的要求），而门自己按 `utf-8` 读它时行首会多出一个 U+FEFF，头注释第一行就不再以 `#` 开头、注释块判空——「本地专属门名单」那半道对账当场变成「脚本没点名」，红信报的是假症状。改成 `utf-8-sig` 之后有无 BOM 都认。这道门只在 CI 文本侧跑，不需要 `gh` 也不需要 `git`：四处抄本全是仓库文件，所以它跟 `check_docs` 第一步一起跑——加门的人先在本地看见它，CI 再兜住。
